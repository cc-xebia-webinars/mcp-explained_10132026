# Two-Hour Technical Webinar

This CLAUDE.md file serves as a guide for preparing the instructor materials for the webinar regardless of topic. This file is copied from webinar to webinar, so keep it free of anything specific to one webinar. Webinar-specific content lives in two places:

- The repo `README.md` holds the title, description, agenda, and the slide PDF file name.
- The `demos/CLAUDE.md` file holds the webinar-specific demo instructions, such as the AI tools and libraries the demos use.

Because the repo is copied from the previous webinar, the `demos/README.md` file, the demo folders, and the slide deck in the `docs` folder may still hold the previous webinar's content. Replace them with content for this webinar rather than editing them.

## Overview

This is a repo for a 2-hour webinar. The webinar runs for 1.5 hours during the 2-hour session: about 20 minutes of slides and about 70 minutes of demos. You will create the number of demos appropriate for the session. The slide deck should cover all of the key points in the agenda and support the demos effectively.

There is no separate question-and-answer segment. People ask questions as the presenter goes, and the presenter answers them during the slides and while the demos run. Don't plan a Q&A block in the timing, and don't add a questions slide to the deck.

The repo `README.md` contains the title, description and agenda for the webinar. The repo will contain a slide deck in the `docs` folder, demos in the `demos` folder, and instructor materials in the `instructor` folder. Before delivery of the webinar, the presenter will delete the `instructor` folder.

The presenter name is "Eric Greene", the company is "Xebia". The presenter's email address is "eric.greene@xebia.com". There is no delivery date. The presenter's email address should be listed on the first and last slides.

The audience will be technical professionals interested in the topic described in the repo `README.md`. Assume they are comfortable with a terminal and with reading code, but do not assume they have used the specific tools the webinar covers.

If you need a fact about this particular webinar that isn't in the `README.md` file or `demos/CLAUDE.md`, such as the presenter name, ask the presenter rather than inventing one.

## Folders

### docs Folder

The deck can have up to 20 slides. The non-content slides are the title slide, the agenda, one hand-off slide for each demo, next steps, and a closing slide with the presenter's contact details. Use the rest of the 20 for content slides. Use the `Xebia PPT General Template.pptx` file in the `instructor` folder as the template for the slide deck. The deck is a PPTX file named after the PDF file name (minus the extension) found in the repo `README.md` file.

The content slides should cover the agenda in the `README.md` file. When there are more content slides than agenda items, give the extra slides to the topics that carry the most weight for the demos. Include speaker notes on every slide. The notes are a summary for the presenter's own reference; the word-for-word script lives in the `instructor` folder.

The deck is generated by a Python script, `instructor/build_deck.py`, which builds it from the template with `python-pptx`. Never edit the PPTX by hand, because the next build overwrites it; change the script and rebuild. The `instructor/CLAUDE.md` file describes the script.

After every build, produce a new PDF from the PPTX file. Use LibreOffice, which is installed locally but is not on the PATH. This command is for PowerShell:

```
& "C:\Program Files\LibreOffice\program\soffice.exe" --headless --convert-to pdf --outdir docs docs\<slide-deck-name>.pptx
```

The conversion fails quietly if the PPTX file is open in PowerPoint, so close it first.

### demos Folder

The demos should show the tools and the workflow the webinar teaches, not just the finished code. Any application code produced along the way will be written in Python, and the `uv` tool will be used to configure virtual environments for each demo and run them.

Each demo lives in its own folder under `demos`, named `##-<demo-name>` with a two-digit number and a short kebab-case name, for example `01-first-server`. Each demo folder has its own `pyproject.toml` managed by `uv`, pinned to Python 3.14. A demo has to run offline on the presenter's machine without paid services or API keys, apart from the AI tools and outside services named in `demos/CLAUDE.md`. No single demo should take more than 20 minutes to walk through.

When a demo needs a sample database, the demo code builds and seeds it when the demo runs. Never commit the database file; the repo `.gitignore` already excludes `*.db` and `*.sqlite3`. The `.gitignore` also excludes any folder named `scripts`, so don't put seed code or other demo code in a folder with that name.

Each demo will have a `README.md` file containing the instructions for the demo and presentation trail. The presentation trail is for the presenter and student to follow during the webinar. Each step in the trail should mention the file being reviewed and explain the code. The demo instructions are for the presenter and students, and they should open with any tools the student needs installed before starting. The `demos` folder should have a `README.md` file that provides a list of all of the demos, a short name and description, and a link to the demo `README.md` file.

When writing the demo `README.md` files:

- Write for the instructor and the student together. Do not include instructions meant only for the speaker in the demo content; those belong in the teaching guide in the `instructor` folder.
- For command-line code blocks, there should be only one command per block so the student can easily copy and paste it when the markdown file is rendered in a web browser.
- Write in a clear and concise manner, so each step is easy to follow for both the instructor and the student.
- Guide the learner through the material in a way that feels natural and engaging, without overwhelming them.

Webinar-specific demo instructions are located in the `CLAUDE.md` file in the `demos` folder.

### instructor Folder

Use the `CLAUDE.md` file in the `instructor` folder as a guide for preparing the instructor materials.

## Content Style

- Humanize the language in all of the content including the slides, code comments, and other documents.
- The content should sound like a professional, corporate technical trainer wrote the content. Professional doesn't mean stiff; avoid overly formal language.
- Avoid jargon and overly complex language; aim for clarity and simplicity.
- Do not use short declarative zingers. The language should be professional.
- Contractions are allowed and encouraged.
- Unbalanced sentences are acceptable if they contribute to a more natural, human-like flow of the content.
- Ensure all content is appropriate for a professional and corporate audience.
- Maintain a consistent tone and style throughout all materials, including slides, code comments, and documentation.
- Slides should not be dense. Keep content slides to six bullets or fewer, and keep each bullet under a dozen words. Code on a slide should fit comfortably without shrinking the font.
- Each artifact reads a little differently. Slides can use fragments. The script is meant to be read aloud, so it should sound like speech. Code comments explain why the code does what it does, not what it does.

## Definition of Done

The slide deck, the PDF, the teaching guide, the script, and the demos drift apart easily. After any change, work through this list:

- The PPTX was rebuilt with `instructor/build_deck.py`, and the PDF in the `docs` folder was regenerated from it.
- The slide count and the agenda in the `README.md` file still match the deck.
- Every slide has speaker notes, and the script in the `instructor` folder matches the current slides.
- Every demo runs clean with `uv` from a fresh clone: `uv sync --locked` succeeds in each demo folder, every command in the demo's `README.md` runs as written, and any sample database is created from scratch.
- Every relative link in the `README.md` files resolves.
- Nothing in the `docs` or `demos` folders depends on the `instructor` folder, since the presenter deletes it before delivery.
